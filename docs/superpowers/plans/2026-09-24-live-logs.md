# Live Logs Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Repository instructions prohibit subagents.

**Goal:** Opening a stack's Logs tab automatically loads recent container logs and keeps the displayed output current until the tab closes, without a Load logs or Refresh button.

**Architecture:** Reuse `/api/v1/stream` and its `logs:<stackId>` topic. The current backend publishes a bounded, redacted, latest-500-lines snapshot only after `POST /stacks/:id/actions/logs`; it does not follow Docker logs continuously. Subscribe before requesting the first snapshot, then request fresh snapshots every five seconds after each request settles. Render the latest WebSocket snapshot, with explicit loading, error, reconnecting, and gap states. Keep this in the stack feature; no backend or new dependency is needed.

**Tech Stack:** Preact hooks, TypeScript, Vitest with Testing Library, existing HTTP client and WebSocket stream.

**Spec:** User request in this conversation, 2026-09-24: automatically load and continue streaming Logs, reuse existing streaming, cover loading/error/reconnect/cleanup, remove the Load logs button.

## Global Constraints

- Preserve the backend's 500-line, bounded and redacted snapshot behavior; cap rendered output at 65,536 characters as the current page does.
- Never overlap log action requests from this tab; a request completes before the next five-second timer starts.
- Do not change or discard the existing untracked `useStackLogs.ts` and `useStackLogs.test.ts` without reviewing them. They are draft work already present in the worktree.
- Follow repository rules: regression test before behavior change, Prettier, focused affected tests, typecheck, build, and no subagents.

## Review Focus

- Entering Logs with no prior log operation: show loading, subscribe, then start a log action automatically.
- A slow log action: do not start another action or a concurrent refresh while it is pending.
- A WebSocket gap or malformed event: keep the last safe output visible and request a fresh snapshot; report the recovery state.
- A failed action or failed session refresh: show an error and continue bounded retries while the tab remains open.
- Switching tabs, stacks, or unmounting during an in-flight action/reconnect: close the socket, clear timers, and ignore late results.
